# PWA Phases 2, 3, 4, 6 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish the PWA — a controlled install experience, an offline mode that blocks every mutation and recovers by itself, and a verification pass — without new dependencies.

**Architecture:** Phase 1's service worker already ships (`apps/web/public/sw.js`, cache `rcb-v1`, static-only). This plan adds three client pieces and one service-worker change. The app has **72 raw `fetch('/api/...')` call sites and no shared HTTP helper**, so offline blocking is done once by wrapping `window.fetch` in a mounted client component rather than editing 72 sites. Decision logic lives in pure functions in `lib/` so it is unit-testable without a browser; the components are thin shells around them.

**Tech Stack:** Next 16.2.7 App Router, React 19, Tailwind v4, zustand, `lucide-react` (already a dependency), `node:assert` + `tsx` for tests (the repo's existing convention — see `apps/web/lib/sw.test.ts`).

**Spec:** `.skill/pwa-phase-2.md`

## Global Constraints

- **No new dependencies.** Not to `package.json`, not to the lockfile.
- **No new env vars, no SQL migrations.** Phase 5 (push notifications) is deferred by the user's decision and is out of scope for this plan. When it lands: send is admin-only, guarded by the existing `requireAdminPassword` in `apps/web/app/api/lib/middleware.ts`.
- **Preserve existing functionality, authentication and routing.** No existing route, API handler, Supabase call or auth path changes behaviour.
- Never cache authenticated HTML, `/api/*`, JWT-authorised responses or Supabase user data — the Phase 1 rule, still binding.
- Offline is **read-only**: do not queue mutations, do not allow offline data entry.
- Error envelopes must match the app's existing shape, `errorResponse(code, message)` from `@rcb-2.0/shared`, so existing UI error handling renders a message instead of crashing.
- Tests run as `npx tsx apps/web/lib/<name>.test.ts` and print one `<name>: ok` line on success.

## Review Focus

1. **Double-installed fetch wrapper.** React 19 StrictMode runs effects twice in dev; wrapping `window.fetch` twice would double-block or recurse. Pinned in Task 2, Step 1.
2. **A shared Response read twice.** Deduplicating in-flight submissions hands one `Response` to two callers, and a body can only be read once — the second `.json()` throws. Each caller must get a `.clone()`. Pinned in Task 3, Step 1.
3. **`beforeinstallprompt` fires before React mounts.** Chrome dispatches it very early; a listener registered in a `useEffect` can miss it entirely and the button never appears. Pinned in Task 1, Step 1 — `createInstallCapture` starts listening at module evaluation time and replays what it already caught to a late subscriber.
4. **iOS browsers that are not Safari.** Chrome and Firefox on iOS cannot add to the home screen, so showing Safari's Share-sheet instructions there is wrong advice. Pinned in Task 1, Step 1.
5. **Blocking `/api/` offline must not break the login screen.** `/login` posts to `/api/auth/login`; if the synthetic offline response does not match the app's envelope, the page throws instead of showing "you're offline". Pinned in Task 2, Step 1.

**Interfaces:**
- Consumes: nothing from Task 1.
- Produces:
  - `isApiRequest(url: string, origin: string): boolean` — true for same-origin `/api/*`
  - `offlineResponse(): Response` — 503, JSON body `errorResponse('OFFLINE', 'You are offline. This action needs a connection.')` from `@rcb-2.0/shared`, `Content-Type: application/json`
  - `installOfflineGuard(win: GuardWindow, onBlocked?: () => void): () => void` — wraps `win.fetch`, returns an uninstall function; **idempotent**: calling it on an already-guarded window returns an uninstall for the existing guard and does not wrap twice. `onBlocked` fires once per refused request and is how `OfflineGuard` learns that a reload is owed on reconnect.

- [ ] **Step 5: Implement `apps/web/components/OfflineGuard.tsx`**

`'use client'`. On mount: `installOfflineGuard(window)`, and subscribe to the `online` and `offline` window events; uninstall and unsubscribe on unmount. Holds `offline` state, initialised from `navigator.onLine` **inside the effect** (never during render — it would mismatch the server HTML).

Renders, while offline, a fixed banner at the bottom of the viewport: "You're offline — showing the last loaded page. Actions are paused." Use the site tokens (`bg-dark-card`/`bg-light-card`, `border-accent/30`, `text-accent`) and `lucide-react`'s `WifiOff`. Give it `role="status"` and `aria-live="polite"`. Render nothing while online.

Pass an `onBlocked` callback to `installOfflineGuard` that sets a ref. On the `online` event: if that ref is set, call `window.location.reload()`; otherwise just clear the banner. This is the spec's "revalidate data after reconnection" — a reload is the only way to refresh 72 scattered client fetches without touching them, and gating it on `onBlocked` means a user who never hit a blocked request is not reloaded out from under their scroll position.

### Task 3: Duplicate-submission guard (spec Phase 4)

**Files:**
- Modify: `apps/web/lib/offline.ts`

**Interfaces:**
- Consumes: `installOfflineGuard` from Task 2.
- Produces: no new export — the same guard also collapses identical in-flight mutations.

- [ ] **Step 1: Write the failing tests**

```ts
// identical in-flight POSTs collapse into one network call
{
  const win = fakeWindow({ online: true, hang: true });
  installOfflineGuard(win);
  const a = win.fetch('https://rcb.test/api/registrations', { method: 'POST', body: '{"id":1}' });
  const b = win.fetch('https://rcb.test/api/registrations', { method: 'POST', body: '{"id":1}' });
  assert.equal(win.realFetchCalls.length, 1, 'double submit hits the network once');

  win.resolveAll({ ok: true, json: { success: true } });
  const [resA, resB] = await Promise.all([a, b]);

  // Review Focus 2: a body can only be read once, so each caller needs its own clone
  assert.deepEqual(await resA.json(), { success: true });
  assert.deepEqual(await resB.json(), { success: true }, 'second caller can still read the body');
}

// different bodies are different submissions
{
  const win = fakeWindow({ online: true, hang: true });
  installOfflineGuard(win);
  win.fetch('https://rcb.test/api/registrations', { method: 'POST', body: '{"id":1}' });
  win.fetch('https://rcb.test/api/registrations', { method: 'POST', body: '{"id":2}' });
  assert.equal(win.realFetchCalls.length, 2);
}

// GETs are never deduplicated, and a settled request no longer blocks a retry
{
  const win = fakeWindow({ online: true });
  installOfflineGuard(win);
  await win.fetch('https://rcb.test/api/members/me');
  await win.fetch('https://rcb.test/api/members/me');
  assert.equal(win.realFetchCalls.length, 2, 'reads are not deduplicated');

  await win.fetch('https://rcb.test/api/x', { method: 'POST', body: '{}' });
  await win.fetch('https://rcb.test/api/x', { method: 'POST', body: '{}' });
  assert.equal(win.realFetchCalls.length, 4, 'retry after completion is allowed');
}

// a failed submission clears its slot so the user can retry
{
  const win = fakeWindow({ online: true, failWith: new TypeError('network') });
  installOfflineGuard(win);
  await assert.rejects(() => win.fetch('https://rcb.test/api/x', { method: 'POST', body: '{}' }));
  await assert.rejects(() => win.fetch('https://rcb.test/api/x', { method: 'POST', body: '{}' }));
  assert.equal(win.realFetchCalls.length, 2);
}
```

Extend `fakeWindow` with `hang` (never settle until `resolveAll`) and `failWith`.
